### Request and transaction contracts

- `PATCH /files/{file_id}`: existing Bearer resolver runs once before parsing input. Only `name` and/or `description` may be explicitly supplied; an empty object, null name, unknown or immutable field is rejected with sanitized 422. The shared name validator strips input, permits 1–100 Python characters, Unicode L/N categories, ASCII space and exactly `_ - . , ( ) [ ] & + @ '`. Description omission preserves it; null/stripped blank clears it; otherwise trim with maximum 250 characters and no additional alphabet restriction.
- PATCH locks `File.id == file_id AND File.owner_id == current_user.id`, requires `ready`, changes only supplied metadata plus `updated_at`, flushes the existing exact File DTO, commits, then returns HTTP 200. Identity, owner, folder, source name/extension/size, status and creation time are immutable. Public fields remain `id`, `name`, `description`, `original_name`, `extension`, `size_bytes`, `status`, `folder_id`, `created_at`, `updated_at`.
- PATCH never obtains storage or invokes parser/chunker/embedder/Qdrant. Deterministic runtime-call assertions and complete in-memory point ID/payload/vector equality cover that boundary; listing reflects the changed metadata. Real configured-store equality remains Stage 2 work.
- Both endpoints owner-scope every file read. Missing/foreign requests produce exactly 404 `{"error":"File not found","code":"FILE_NOT_FOUND"}`. PATCH processing/deleting and DELETE processing produce exactly 409 `{"error":"File is not ready","code":"FILE_NOT_READY"}`; no storage call or protected state mutation.
- DELETE first locks the owner-scoped row, commits `ready -> deleting` plus `updated_at`, and closes the session. Already `deleting` resumes; it is never restored to ready. Only then does `Storage.delete(UUID)` reuse the existing exact `payload.file_id == str(UUID)` filter, `wait=True` and required completed acknowledgement. Confirmed zero matches are valid.
- After confirmed cleanup, a **fresh**, owner-scoped locked transaction requires deleting if the row remains, deletes it and commits. HTTP 204 has an empty body and follows this final commit. A concurrent authorized in-flight finalizer may already have removed it; that finalization is successful, while a later fresh DELETE of an absent row returns 404.
- Qdrant failure leaves deleting and vectors available for retry; final PostgreSQL delete/commit rejection leaves deleting with vectors absent. Both return failure, preserve unrelated files and retry via the same exact cleanup. Initial marker-commit rejection prevents index access. SQLAlchemy failures use the existing safe database error; Qdrant transport/collection classifications remain unchanged. No raw SQL, credentials or backend exception body is returned.
